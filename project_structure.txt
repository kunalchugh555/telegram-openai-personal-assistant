## Key Design Decisions

- Polling mode (not webhooks): simpler, no HTTPS/domain required, works on always-on GCP e2-micro VM
- Deployed on Google Cloud Compute Engine e2-micro (us-central1-a) — free tier, $0/month hosting
- systemd service on the VM keeps the bot running and restarts it automatically on reboot or crash
- Single token.json for all Google services (Calendar, Tasks, Gmail, Drive scopes in one consent flow)
- token.json generated locally (auth_google.py opens a browser) then copied to the VM via gcloud scp
- SQLite for conversation history: zero infrastructure, survives restarts, good enough for personal use
- DATA_DIR env var controls where token.json and assistant.db live (. locally, ~/app dir on VM)
- Conversation history capped at 20 messages per user to control token costs
- System prompt injected with current datetime AND user location/timezone at each call
- Tool results passed back to GPT before final reply — GPT generates the confirmation message
- All datetimes are timezone-aware using the calendar's own timezone setting
- Bot is private: ALLOWED_USER_ID in .env gates all incoming messages
- "Thinking..." message ("...") sent immediately on audio receipt, then edited to final reply (better UX)
- No TTS — replies are plain text Telegram messages
- Audio input accepts voice notes, audio uploads, and audio documents (filters.VOICE | AUDIO | Document.AUDIO)
- Audio conversion auto-detects the source format via ffmpeg, so any decodable format works
- LLM tool loop is bounded (MAX_TOOL_ROUNDS) so a misbehaving model cannot loop forever
- Calendar/Tasks/Gmail/Drive auth errors short-circuit the LLM loop with a fixed user-facing message
- OpenAI clients are created lazily so the API key is read after .env is loaded
- Gmail: create_draft only stages a draft; send_email sends immediately. GPT drafts by default and
  only sends when the user clearly asks to send.
- Drive uses a read-only OAuth scope (drive.readonly) — drive_tools never writes
- Drive file content is always truncated to 3000 chars; Sheets to 50 rows — protects GPT context
- PDFs are read with pypdf; if pypdf is unavailable, PDF reading degrades to a graceful error
- Weather uses Open-Meteo (free, no API key); US units (Fahrenheit, mph); failures return error payloads
- Daily rain/snow email: bot.py registers a job_queue.run_daily job at 5am (USER_TIMEZONE); sends to
  USER_EMAIL via Gmail if today's weather condition contains rain/snow keywords; GmailAuthError is caught
  and logged without crashing the bot
- Google Maps uses the Directions API (travel time) and Places Text Search API (nearby search); both
  require GOOGLE_MAPS_API_KEY (not OAuth); missing key returns a graceful error payload
- Google Meet: create_event accepts add_meet_link=True; uses conferenceDataVersion=1 and a uuid requestId;
  meet_link is returned in the result dict when generated
- _humanize() in calendar_tools.py now converts all timezone-aware datetimes to USER_TIMEZONE before
  formatting, so tool results always show times in the user's local time
- _system_prompt() in llm.py uses zoneinfo.ZoneInfo(USER_TIMEZONE) for current time so the VM (UTC) shows
  the user's local time, not UTC
- get_weather returns current + today + next 14 days + past 7 days; get_hourly_forecast gives hour-by-hour
  detail for any single day within 92 days back or 14 days ahead (Open-Meteo past_days/forecast_days)
- Web search: OpenAI's native web search is a Responses API tool, not a Chat Completions tool. It is
  exposed to GPT as an ordinary `web_search` function tool whose handler (_web_search in llm.py) calls
  the Responses API. This keeps the proven Chat Completions tool loop unchanged.

## Security posture (audited 2026-05-19, two passes)

Repo / code:
- .env and token.json are git-ignored and never committed (verified via git history)
- SQL: db.py uses parameterized queries — no SQL injection surface
- Code: no eval/exec/subprocess/shell=True; tool dispatch is a hard-coded whitelist
- TLS: no `verify=False` anywhere — all HTTPS traffic verified
- Dependencies: pip-audit clean (pypdf 6.10.2, requests 2.33.0, python-dotenv 1.2.2)

Filesystem:
- .env, token.json, assistant.db are chmod 600 (owner-only) on both local and VM
- No audio temp files leaked — bot.py cleans them up in a finally block

VM OS:
- SSH: PasswordAuthentication=no, PermitRootLogin=no, key-only
- block-project-ssh-keys=true on the instance — project-wide keys cannot SSH in
- unattended-upgrades installed (auto security patches)
- fail2ban active and watching the sshd jail
- No cron jobs, no bash/python history files, only one login user (kunalchugh)

systemd bot service (was 9.6 UNSAFE → now 3.2 OK):
- NoNewPrivileges, PrivateTmp, PrivateDevices, ProtectSystem=strict
- ProtectKernel{Tunables,Modules,Logs}, ProtectControlGroups, ProtectClock, ProtectHostname
- ReadWritePaths limited to the app directory
- RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
- RestrictNamespaces, RestrictRealtime, RestrictSUIDSGID, LockPersonality
- CapabilityBoundingSet emptied; SystemCallArchitectures=native; UMask=0077

GCP:
- VM has NO service account attached — metadata server returns 404 for token requests
- Firewall: only default-allow-ssh (internet → 22), default-allow-internal, default-allow-icmp
- $5 project budget alert at 50/90/100%
- Disk encryption: Google-managed (default, always on)

LLM:
- System prompt has explicit SECURITY RULES against indirect prompt injection
  (treats email/Drive/web-search content as untrusted data; requires user authorization in the
  current turn for send_email/delete_event/delete_task; forbids disclosing secrets)
- Bot is gated by ALLOWED_USER_ID — every handler short-circuits for non-allowed senders

## Environment Variables (see .env.example)

- TELEGRAM_BOT_TOKEN        Telegram bot token from @BotFather
- OPENAI_API_KEY            OpenAI API key
- GOOGLE_CLIENT_ID          Google OAuth client ID
- GOOGLE_CLIENT_SECRET      Google OAuth client secret
- GOOGLE_CALENDAR_ID        Calendar to use (default: primary)
- GOOGLE_TASKS_LIST_ID      Task list to use by default (default: @default)
- ALLOWED_USER_ID           Your Telegram numeric user ID
- USER_NAME                 Your name — injected into the system prompt so GPT addresses you by name
- USER_EMAIL                Your email — destination for daily rain/snow alerts
- USER_LOCATION             Home location for weather and context (e.g. "Dubuque, Iowa")
- USER_TIMEZONE             Your timezone, IANA format (e.g. America/Chicago)
- GOOGLE_MAPS_API_KEY       API key for Google Maps Directions and Places APIs
- DATA_DIR                  Path for token.json and assistant.db (default: .)

## Models

- STT model:         gpt-4o-mini-transcribe   (defined in stt.py)
- LLM model:         gpt-5.4-mini             (defined in llm.py, LLM_MODEL)
- Web search model:  gpt-5.4-mini             (defined in llm.py, WEB_SEARCH_MODEL — must support
                                               the Responses API web_search_preview tool)

## OAuth Scopes (auth_google.py)

- https://www.googleapis.com/auth/calendar        read/write Calendar
- https://www.googleapis.com/auth/tasks           read/write Tasks
- https://www.googleapis.com/auth/gmail.modify    read mail and create drafts
- https://www.googleapis.com/auth/gmail.send      send mail
- https://www.googleapis.com/auth/drive.readonly  read-only Drive access

## Important Notes

- Run auth_google.py once before starting the bot — generates token.json
- Re-run auth_google.py whenever scopes change (e.g. after Gmail/Drive were added)
- Enable Calendar, Tasks, Gmail, and Drive APIs in the Google Cloud project
- Find your Telegram user ID by messaging @userinfobot
- ffmpeg must be installed (handled in Dockerfile; install manually for local dev)
- On Fly.io, token.json must be copied to the persistent volume after first auth
- The bot processes voice notes, uploaded audio files, and text messages — all other types are ignored
- /start replies with a capabilities summary
- /clear wipes conversation history for that user
